## 2026-11-23 additional original Apple request-pool factory trace

The owner-private, exact-hash-gated `IONVMeFamily` 2.1.0 source now confirms a further direct call chain in the constructor/factory: **three alternative top-level pool wrappers forward their incoming `x4` as `x5`**, the underlying pool constructor stores that argument, and a pool helper computes a conditional mask (`w25 &= w24`) before forwarding the resulting value to the per-request allocator. That allocator passes it as factory `w5`; the factory passes it as initializer `x6`. The initializer sets internal request flag bit3 iff `x6` is nonzero; the original Read builder then maps that flag into **CDW0 bit13** (second command byte `BIT(5)`). This is now covered by **79 instruction fingerprints and 17 exact `BL` targets**, verified against the full authentic original executable SHA-256 and synthetic mutation cases.

The next source step identifies a **common source for all three wrapper `x4` values**: the output of a controller virtual method at vtable offset **1440**. The original initializer branches between the three wrappers, but each forwards the returned value in `x22` as `x4`. This further narrows the live uncertainty to the selected controller implementation, its method return and the pool's `w24` mask. The traced data flow **does not establish the live N71's virtual-method return, filter result, or final `BIT(5)` setting**. In particular, class/vtable reachability from an original prelinked driver does not demonstrate that Apple's N71 runtime takes that path. The stage remains **original-source evidence only**, with no physical S3E queue creation, NAND reads/writes or DMA lifetime changes. The only active module on the phone remains the bounded charging supervisor, when its lease is valid.

## 2026-11-23 original Apple constructor-derived controller virtual method choices

A new exact-hash-gated source audit of owner-private original `IONVMeFamily` proves the **method at vtable byte offset 1440 has different implementations in a constructor-linked base/derived pair**. A verified original derived constructor calls the parent constructor and then installs a separate owned `__DATA_CONST.__const` vtable. The base vtable resolves slot 1440 to a two-instruction `return 0` function (`MOV W0,#0; RET`); the derived vtable resolves the same slot to a two-instruction `return 1` function (`MOV W0,#1; RET`). Both adjacent slot 1448 functions follow the corresponding return values. The audit checks prelink identity, full original executable SHA-256, constructor linkage, bounded vtable ownership, original method pointers and **15 exact ARM64 instruction words**, with fail-closed mutation fixtures. Verification tool: `tools/n71_s8000_original_ionvme_vtable1440_gate.py`; tests: `tests/test_n71_s8000_original_ionvme_vtable1440_gate.py`.

**Important qualification:** This proves two source-level class alternatives, **not the dynamic class bound to the real N71 controller**. The physical N71 request-pool initializer's vtable pointer/return remains unverified. Inferring `BIT(5)` from the derived `return 1` would be unsafe; `Read`, I/O queue creation, FlatDMA tag1 publication, NAND access and DMA retirement remain blocked. No source code or original firmware payload was uploaded from the private owner workstation.

3. **Owner-attended hardware preflight:** stable battery reserve preferably at least 50%, physically qualified bounded charger and temperature below the owner's maximum 38°C, healthy VBUS, fresh clean S3E epoch. Do not loosen the user's temperature ceiling or silently alter brightness.
4. **One real read-only trial:** before any physical I/O SQ/CQ or read execution, qualify all four DART streams, new owned pages, tag1 TCB/SGL and queue completions. 5. **Read-only block device:** only after safe repeated physical reads and adequate DMA lifetime evidence; disable automount. NAND writes, formatting or installing Linux on the internal media require separate explicit approval, backup and recovery plan.
